# Независимое ревью кода

Навык задаёт, как проверять изменение перед слиянием: что прочитать, по каким осям смотреть, как оценить серьёзность замечания и как оформить вердикт. Ревьюер — не автор изменения и работает в отдельной сессии без истории автора: видит только задачу, критерии приёмки и diff. Только чтение: код не меняется, результат — отчёт.

Навык — общая рамка. Предметные чек-листы — в разделах «Проверки» профильных навыков (`test-strategy`, `privacy`, `performance`, `documentation` и навыков, которые добавил проект). Проверку безопасности делает `independent-security-review`.

## Прочитай сначала

- [AGENTS.md](../../../AGENTS.md) — [инварианты](../../../AGENTS.md#инварианты) (нарушение — блокер) и правила работы агентов.
- [CONTRIBUTING.md](../../../CONTRIBUTING.md) — правила кода, [документации](../../../CONTRIBUTING.md#документация) и [работы с AI-агентами](../../../CONTRIBUTING.md#работа-с-ai-агентами).
- [Агенты и рабочий процесс](../../../docs/agents.md#рабочий-процесс) — место ревью в задаче и кому передавать дальше.
- [Индекс ADR](../../../docs/adr/README.md); ADR, на которые ссылается задача.
- Архитектура кода, если в проекте есть (например `docs/architecture.md`).
- Задача: владелец, разрешённые файлы, вход, критерии приёмки. Diff: `git diff <база>...<голова>` целиком. Если коммитов ещё нет — рабочее дерево: `git status`, `git diff`, `git diff --cached` и неотслеживаемые файлы (`git ls-files --others --exclude-standard`), каждый читается целиком.
- Шаблон отчёта и шкала серьёзности — [references/review-report.md](references/review-report.md).

## Шаги

1. **Свежий контекст.** Получи только задачу, критерии приёмки, базовый и проверяемый коммит (или снимок рабочего дерева). Переписку автора и его выводы не читай. Нет задачи или критериев приёмки — остановись и задай вопрос владельцу ([задача агента](../../../docs/agents.md#задача-агента)).
   **Правило:** ревьюер не автор изменения и не одобряет собственный PR.
   Готово, когда в отчёте записаны база и голова (или «рабочее дерево» и время снимка) и ссылка на задачу.
2. **Карта изменения.** Перечисли затронутые области: модули кода, схема данных и миграции, публичные контракты (API, события), авторизация и секреты, конфигурация и зависимости, CI, `docs/`, агенты и навыки. Сверь со списком разрешённых файлов.
   Готово, когда каждый файл diff отнесён к области, а файлы вне разрешённых отмечены.
3. **Ось «Спецификация».** Каждый критерий приёмки — выполнен, не выполнен или не проверяем. Для выполненного назови тест или строку кода, которые это доказывают. Лишнее поведение сверх задачи — тоже замечание.
   Готово, когда у каждого критерия есть статус и доказательство.
4. **Ось «Стандарты».** Пройди [инварианты](../../../AGENTS.md#инварианты), правила CONTRIBUTING и связанные ADR. Для каждой затронутой области прочитай `SKILL.md` профильного навыка и пройди его раздел «Проверки». Для `docs/` — «Проверки» навыка `documentation` и [правила ADR](../../../docs/adr/README.md): принятый ADR меняется только статусом, строкой связи, исправлением опечатки или битой ссылки. Документы сильнее общих привычек: если код следует ADR, а общая практика говорит иначе — замечания нет.
   **Правило:** нарушение инварианта из `AGENTS.md` или документированного правила (ADR, CONTRIBUTING) — блокер. Сценарий отказа для него не нужен, достаточно ссылки на нарушенную строку документа.
   Готово, когда по каждой области назван применённый чек-лист.
5. **Тесты.** Новое поведение покрыто тестом, тест падает без изменения и проходит с ним. Конкурентный доступ и изоляция данных проверяются на реальной инфраструктуре, а не на моках (`test-strategy`). Приложи вывод `npm run check` и, для документации, `npm run check:docs`, для агентов и навыков — `npm run agents:check` от автора или CI. Сам запускай, только если [полномочия](../../../docs/agents.md#правила-и-полномочия) и песочница это позволяют.
   Готово, когда вывод команд приложен или в отчёте записано «проверки не предоставлены», а непокрытое поведение перечислено.
6. **Серьёзность.** Каждое замечание: файл:строка, что не так, сценарий отказа (вход → неверный результат), ссылка на документ, уровень по шкале из references.
   **Правило:** без сценария отказа замечание — не выше «пожелания», кроме нарушения документированного правила (шаг 4).
   Готово, когда у каждого замечания есть файл:строка, суть, ссылка на документ, уровень и сценарий отказа или нарушенное правило.
7. **Передача профильным ревьюерам.** Авторизация, секреты, криптография, внешний ввод, зависимости, чувствительные инварианты → `security-reviewer`. Персональные данные → `privacy-specialist`. Горячие пути и нагрузка → `performance-engineer`. Сам эти области не одобряешь.
   Готово, когда в отчёте указано, кому и что передано, или «передача не нужна» с причиной.
8. **Вердикт.** «Можно сливать» — нет блокеров и важных замечаний без принятого решения. «Нужны изменения» — иначе. Открытые вопросы к владельцу не решаются ревьюером.
   Готово, когда отчёт передан автору (например комментарием к PR), а код не изменён.

## Проверки

- [ ] Ревью шло в отдельной сессии, ревьюер не автор изменения.
- [ ] Каждый критерий приёмки имеет статус и доказательство.
- [ ] Каждый инвариант из `AGENTS.md` проверен по затронутым областям; список не копируется в отчёт, нарушенный инвариант цитируется со ссылкой.
- [ ] Вывод `npm run check` (и `npm run check:docs`, `npm run agents:check` при соответствующих правках) приложен, либо записано «проверки не предоставлены».
- [ ] У каждого замечания есть файл:строка, ссылка на документ, уровень и сценарий отказа или нарушенное правило.
- [ ] При правке `docs/adr/` принятые ADR изменены только в допустимых местах.
- [ ] Безопасность передана `security-reviewer`, персональные данные — `privacy-specialist`, если затронуты.

## Вне области

- Исправление кода — автор изменения.
- Проверка безопасности — `independent-security-review`; архитектурные решения — `architecture-decisions`.
- Решение о слиянии и релизе — человек.
