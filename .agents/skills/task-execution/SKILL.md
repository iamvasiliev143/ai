# Выполнение задачи

Навык ведёт исполнителя по шагам рабочего процесса так, чтобы результат можно было проверить независимо: изменение в пределах разрешённых файлов, код с тестами, доказательства проверок и отчёт передачи. Что именно строить, решают требования и ADR; навык отвечает за то, как довести задачу до ревью.

## Прочитай сначала

- [AGENTS.md](../../../AGENTS.md) — инварианты, ограничения, таблица навыков.
- [docs/agents.md](../../../docs/agents.md#задача-агента) — шаги задачи агента, состояния, правила и полномочия.
- [CONTRIBUTING.md](../../../CONTRIBUTING.md) — правила кода и документации.
- Навыки стека проекта из таблицы в `AGENTS.md` — по затронутой области.
- Формат отчёта передачи: [references/handoff-report.md](references/handoff-report.md).

## Шаги

1. **Готовность.** Найди в задаче владельца, разрешённые файлы, входной контракт и критерии приёмки. Чего-то нет — задай вопрос владельцу и не начинай.
   Готово, когда все четыре пункта названы явно, а критерии приёмки проверяемы.
2. **Контекст.** Прочитай навыки своей зоны, канонические документы и ADR, на которые они ссылаются, затем код задачи. Документы молчат или расходятся — вопрос владельцу со ссылками на строки, а не молчаливый выбор.
   Готово, когда для каждого критерия приёмки понятно, какой код и какой документ его определяют.
3. **План.** Перечисли файлы, которые изменишь, и тесты, которые докажут критерии. Файл вне разрешённых или новое решение (зависимость, схема, контракт, инфраструктура) — сначала согласование с владельцем и ADR по `architecture-decisions`.
   Готово, когда план не выходит за разрешённые файлы или выход согласован.
4. **Изоляция.** Отдельная ветка от актуального `main` и отдельный worktree. В `main` не пишешь.
   Готово, когда `git status` показывает рабочую ветку задачи.
5. **Реализация и тесты.** Код и тесты в одном изменении. Для ошибки — сначала тест, который падает, затем исправление. Инварианты из `AGENTS.md` не нарушаются даже временно.
   Готово, когда каждый критерий приёмки покрыт тестом или описанной ручной проверкой.
6. **Проверки.** `npm run check`; после правки документов, агентов или навыков — `npm run check:docs`. Падение не обходишь отключением проверки или теста.
   Готово, когда команды завершаются с кодом 0, а их итог записан для отчёта.
7. **Самопроверка.** Пройди «Проверки» этого навыка и навыков зоны. Прочитай свой diff целиком как ревьюер: лишние изменения, отладочный код, секреты, закомментированный код.
   Готово, когда в diff только то, что требует задача.
8. **PR и передача.** Коммиты по Conventional Commits, PR с отчётом передачи по шаблону `.github/pull_request_template.md`. Изменения авторизации, секретов, границ доверия и инвариантов помечаешь «нужна независимая проверка» и называешь `security-reviewer`.
   Готово, когда PR открыт, отчёт заполнен, следующий владелец назначен, а ревьюер — не ты.
9. **Исправления по ревью.** Каждое замечание — исправление или аргументированный ответ. Не больше 3 повторов шага; дальше — вопрос владельцу.
   Готово, когда блокирующих замечаний нет.

## Проверки

- [ ] Изменены только разрешённые файлы или выход за них согласован.
- [ ] Каждый критерий приёмки подтверждён тестом или описанной проверкой.
- [ ] `npm run check` (и `npm run check:docs`, если нужно) — код 0, итог в отчёте.
- [ ] В diff нет секретов, `.env*`, реальных персональных данных, отладочного кода.
- [ ] Новые термины в глоссарии, новые решения — в ADR.
- [ ] Отчёт передачи заполнен; собственный PR не одобряешь.

## Вне области

- Требования и критерии приёмки — `product-requirements`.
- Декомпозиция и статусы — `delivery-planning`.
- Стратегия и состав тестов — `test-strategy`.
- Ревью — `independent-code-review`, `independent-security-review` в отдельной сессии.
- Методики стека (фреймворки, библиотеки) — навыки стека проекта.
