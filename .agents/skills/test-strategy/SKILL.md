# Стратегия тестирования

Навык превращает критерии приёмки задачи в тест-план, выбирает уровень каждого теста и задаёт обязательные сценарии для инвариантов, доступа и внешних интеграций. Результат — тесты и отчёт тестирования с доказательствами. Продуктовый код ради прохождения теста не меняется: дефект возвращается исполнителю.

Конкретные инструменты тестирования выбирает проект и фиксирует в ADR или в описании стека; навык от них не зависит.

## Прочитай сначала

- [AGENTS.md](../../../AGENTS.md) — [инварианты](../../../AGENTS.md#инварианты): каждый затронутый инвариант должен иметь тест.
- [CONTRIBUTING.md](../../../CONTRIBUTING.md) — команды проверок и правила кода.
- [Индекс ADR](../../../docs/adr/README.md) — решения о тестовых инструментах и обязательных тестах.
- Тест-план, матрица приёмки и описание стека, если в проекте есть (например `docs/test-plan.md`, `docs/acceptance-matrix.md`, `docs/tech-stack.md`).
- Каталог сценариев и шаблон отчёта — [references/test-catalog.md](references/test-catalog.md).

## Шаги

1. **Источник требований.** Выпиши критерии приёмки задачи и связанные строки матрицы приёмки или контракта. Каждому требованию — ID.
   Готово, когда у каждого критерия есть ID и ссылка на документ.
2. **Уровень теста.** Для каждого требования выбери самый дешёвый уровень, который его доказывает: модульный (правила, расчёты, валидация), интеграционный на реальной инфраструктуре (база, очередь, кеш: транзакции, блокировки, идемпотентность, изоляция данных), e2e через публичный интерфейс (маршруты, права, формат ошибок, вебхуки), браузерный (экраны, доступность).
   **Правило:** конкурентный доступ, идемпотентность и изоляция данных — только на реальной инфраструктуре, не на моках.
   Готово, когда у каждого требования назван уровень и файл теста.
3. **Инварианты.** Для каждого затронутого [инварианта](../../../AGENTS.md#инварианты) — тест, который упадёт при его нарушении. Список инвариантов не копируется в тест-план — ссылка на `AGENTS.md`.
   Готово, когда каждый затронутый инвариант имеет тест или запись «не затронут» с причиной.
4. **Конкуренция и сбои.** Параллельный дубль с тем же ключом; повтор с тем же ключом и другим телом; гонка двух операций над одним ресурсом; сбой после записи до фиксации транзакции; таймаут блокировки и повтор; повтор и переупорядочивание входящих событий; потеря ответа внешней системы.
   Готово, когда каждый применимый сценарий из references имеет тест или запись «неприменимо» с причиной.
5. **Доступ и данные.** Для каждого нового хранилища с данными пользователей — тест «без контекста доступа → нет данных». Для каждого маршрута чтения — тест с двумя владельцами данных, чужой ресурс → `404` (или принятый в проекте код). Для чувствительной команды — тест на отсутствие прав и на обход подтверждения, если оно требуется.
   Готово, когда каждый новый маршрут и хранилище имеют такие тесты.
6. **Соответствие контракту.** Если есть внешний контракт (OpenAPI, схема событий, контракт партнёра) — тесты называются ID сценария контракта и прогоняются против зафиксированной версии контракта. Изменение контракта без версии — блокер.
   Готово, когда для каждого затронутого сценария контракта есть тест с тем же ID в названии.
7. **Методы, требующие решения.** Property-тесты, нагрузочные и мутационные тесты — если нужного инструмента нет в принятом стеке, нужен ADR. До решения — простая реализация без новой зависимости (генератор с фиксированным сидом, замеры в интеграционных тестах).
   Готово, когда потребность в инструменте записана как вопрос владельцу, а не добавлена зависимостью.
8. **Quality gates и отчёт.** `npm run check` зелёный, при правке документации — `npm run check:docs`. Отчёт по шаблону из references; для строки матрицы приёмки — ID строки, среда, версия сборки и результат.
   Готово, когда отчёт содержит требования, тесты, итог команд и дефекты с шагами воспроизведения.

## Проверки

- [ ] У каждого критерия приёмки есть тест или запись «не проверяем» с причиной.
- [ ] Каждый затронутый инвариант из `AGENTS.md` имеет тест.
- [ ] Тесты конкуренции, идемпотентности и изоляции работают на реальной инфраструктуре.
- [ ] Тесты контракта названы ID сценариев контракта.
- [ ] Нет реальных персональных данных, ключей и токенов — только синтетика.
- [ ] Нет новых тестовых зависимостей без ADR.
- [ ] `npm run check` зелёный; вывод приложен к отчёту.
- [ ] Каждый найденный дефект возвращён исполнителю с шагами воспроизведения, продуктовый код не исправлен ради теста.

## Вне области

- Независимая проверка безопасности — `independent-security-review`; нагрузочные замеры и профилирование — `performance`.
- Реализация исправлений — `task-execution` у исполнителя.
- Выбор новых инструментов тестирования — `architecture-decisions` и владелец.
